# Operator guide

1. Run `Run.cmd`. The server listens without opening the camera when no clients are present.
2. Select the camera and adjust its capture settings. Connect the test client to the server host/IP and port (8765 by default).
3. The camera opens automatically. Present an OEPS version 1/2/C label, a supported supplier barcode, or other barcode text. Supplier labels become version 3; unrecognized text becomes raw X. Data Matrix, QR, Aztec and linear formats are enabled. Version 1/3 quantity is a string; version 2 carries internal IDs and printed numbers.
4. Inspect the latest data on the client. The checksum and debug fields stay on the server.
5. On the server, enable **Show details (debug)** to see the preview, latest JSON and live diagnostics for structured, raw and suppressed readings. Version 3 requires valid quantity and at least one of a valid OEPS PN or a nonempty MPN; either missing identifier is shown as unavailable and sent as null. All decoded codes that fail versions 1/2/3/C are forwarded as X, with the validation reason retained in diagnostics. This includes missing supplier quantity, missing both identifiers and failed OEPS CRCs. No reading or image is saved.

Under **Latest data**, **Label versions & JSON** opens a reference window with a version selector, routing/validation rules and matching barcode/JSON examples for 1/2/3/C/X. The reference is read-only and can remain open while the scanner runs. The test client automatically displays the fields for the latest label's version. Upgrade both client DLLs for C support in another application. These features are included in v0.2.0; update older installations and both client DLLs.

No clients for one minute closes the camera. A new client reopens it. Enable **Keep camera connected (debug)** to operate without clients.

Command labels use `C*<command>*<checksum>`. For example, scan `C*For Odoo OUT*14C79D4D` to receive `{"label_version":"C","command":"For Odoo OUT"}`. The scanner verifies the same CRC-32 used by versions 1/2 and displays the command. The connected application decides what it does. New command names do not need a scanner update; bad checksums or malformed command labels become raw X. Camera commands use the 500 ms filter; reader commands are sent on every scan. The full rules and ready-to-print example are under **Version C — Commands** in **Label versions & JSON**.

**Show details (debug)** is off by default: the server uses a fixed 900 × 530 window containing camera, barcode reader and network controls. Enable it for the resizable detailed view. The choice is saved for the next launch. Hiding details pauses preview encoding and rendering while scanning and delivery continue. In the detailed view, **Enable camera preview** separately controls preview work; its preference is preserved when hiding details.

## Bluetooth barcode reader

1. Configure Bluetooth SPP and pair the reader in Windows. The BCST-73 on this computer exposes outgoing COM3 and incoming COM4; only COM3 is offered. Other SPP devices are allowed too. Scans arrive through serial data without typing into other applications.
2. Select the reader in **Barcode reader** (Refresh discovers paired devices). Connect your client to **Reader WebSocket**, default `ws://<server>:8766/labels`. The first client opens the reader immediately. Wake it if asleep; connection failures retry every five seconds while demand remains.
3. Camera clients use **Camera WebSocket**, default `ws://<server>:8765/labels`. Both ports are configured together using **Apply ports** and must differ. A failed port change restores the previously working listeners when possible. Each port sends only its own source, with the same JSON schemas and existing client DLL API. A legacy camera port of 8766 is retained; the new reader port then defaults to 8767.
4. Each source disconnects after **one minute without its own clients**, regardless of clients on the other port. Separate **Keep camera connected (debug)** and **Keep reader connected (debug)** overrides keep the corresponding hardware open. The reader Connect button enables its debug override when no reader client is present; Disconnect clears it and closes immediately. While reader clients remain connected, the manual Disconnect button is disabled. Uncheck Enable camera if camera capture is not wanted.
5. Configure **UTF-8 output** and **Add Enter after Barcode**. The physical BCST-73 tested here sends CR+LF (`0D 0A`). Disable extra prefixes, timestamps and character replacement. Preserve GS/RS/EOT. The [Inateck SPP manual](https://cdn.shopify.com/s/files/1/0623/5809/4063/files/1BCST-73-EN.pdf?v=1706164588) has ending settings on printed page 41 and GS substitution on page 52. Encoding choices vary by firmware; a generic Unicode option alone does not establish UTF-8 output.

**Fast scans (CR+LF)** is enabled by default. Every CR+LF terminates a scan immediately, including several scans arriving in a single read. Identical scans are all forwarded: there is **no reader cooldown or duplicate suppression**. Split Bluetooth chunks and split UTF-8 sequences are reassembled. Tabs, RS/GS/EOT, NUL, standalone CR/LF and other characters are retained, but embedded **CR+LF separates readings** in this mode. Reader output must include CR+LF, not CR alone. Invalid UTF-8 frames are rejected. Oversized or unfinished frames are discarded through their next delimiter to avoid forwarding their tail as a new raw label.

For labels with embedded CR+LF, disconnect reader clients and the reader, then disable **Fast scans**. Multiline mode accepts CR or CR+LF suffixes, preserves internal and original trailing newlines, and completes a terminated burst after 250 ms of silence. Unterminated chunks are retained for up to five idle seconds. Leave at least 250 ms between scans in this mode; adjacent scans can otherwise merge, and a pause after an embedded ending can resemble a scan boundary. Arbitrary binary framing requires a device protocol with length or escaping. The application cannot recover characters already transformed by the reader.

Discovery uses Windows outgoing SPP service identities and the current COM map. Incoming/non-SPP ports are excluded; SPP compatibility alone does not prove a device is a barcode reader. The saved identity is resolved again before opening, allowing COM reassignment. The port opens exclusively; an occupied port fails visibly. Bluetooth loss detection depends on the Windows serial driver.

Camera readings retain the **500 ms per-payload duplicate filter**, for every version including X. Reader scans bypass that filter completely in both modes. No source adds a replay backlog for absent clients. Restart local applications after updating the code.
