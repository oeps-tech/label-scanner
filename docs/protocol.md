# Data-only WebSocket protocol

Camera and Bluetooth SPP reader input use the same classification and JSON schemas, but separate listeners. Camera readings use the 500 ms duplicate gate; reader readings are never deduplicated. No source/port metadata is added to messages. For reader scan boundaries, see the [operator guide](operator-guide.md#bluetooth-barcode-reader).

Endpoints: camera `ws://<host>:8765/labels`, barcode reader `ws://<host>:8766/labels` (ports configurable and distinct). Each sends only its own source. The first client on a source opens that hardware; the last client leaving starts its one-minute idle timer. Each source has a separate debug override. No hello/subscription command is needed. Each decoded code is routed to exactly one JSON schema: a validated version 1/2/3/C, otherwise X. OEPS versions 1/2/C validate CRC before broadcast; versions 3/X require no OEPS checksum. No checksum is transmitted.

Version 1 has exactly four fields: `label_version` (integer 1), `oeps_pn`, `lot` and `quantity` (strings). Example: `{"label_version":1,"oeps_pn":"OEPSA010123","lot":"0926-TRAY-Q5R2","quantity":"0"}`.

Version 2 has exactly five fields: `label_version` (integer 2), `sales_order_id` and `out_id` (positive integers up to 2147483647), `document_name` and `out_number` (strings). Example: `{"label_version":2,"sales_order_id":857,"document_name":"S/2680","out_id":1923,"out_number":"WH/OUT/00567"}`. `document_name` is the printed sales order number, not Odoo's `name`. No version 1 fields or null placeholders are included. Record IDs refer to `sale.order` and `stock.picking` respectively; the receiving application supplies its Odoo base address for links. The scanner does not look up records or verify their relationship.

Version 3 has exactly four fields: `label_version` (integer 3), `oeps_pn` (string or null), `mpn` (string or null), `quantity` (string). Example: `{"label_version":3,"oeps_pn":null,"mpn":"74LVC4245AD,118","quantity":"200"}`. It requires **valid quantity AND (valid OEPS PN OR nonempty MPN)**. Either identifier may be null, but both cannot be missing. OEPS PN uses the version 1 grammar. Supplier codes failing this rule or structural checks are sent as X, preserving the complete original text.

Version C has exactly two fields: `label_version` (string `"C"`) and `command` (string). Example: `{"label_version":"C","command":"For Odoo OUT"}`. Barcode format: `C*<command>*<checksum>`, with CRC-32/IEEE over exact ASCII `C*<command>` and eight uppercase hexadecimal checksum characters. Command text is nonblank printable ASCII without `*` or controls, up to 4,085 characters; the complete barcode is at most 4,096 characters. Spaces and case are preserved. There is no fixed command list; clients define their own supported commands and behavior. The scanner forwards commands without executing them. Invalid command labels become raw X. The checksum is omitted from JSON.

Version X has exactly two fields: `label_version` (string `"X"`) and `raw` (string). Example: `{"label_version":"X","raw":"OEPS-1234\tvalue\r\nnext"}`. There is no content validation or checksum. JSON parsing restores the original tabs, CR/LF, RS/GS/EOT and Unicode characters. No literal `X*` prefix is added. X is the universal fallback when versions 1, 2, 3 and C fail validation; valid OEPS/supplier/command labels do not also produce X. This includes failed OEPS checksums and recognized suppliers with malformed/ambiguous fields, invalid quantity or missing identifiers.

The endpoint is receive-only for clients. No application acknowledgements, feedback, image channel, persisted backlog or scan history. WebSocket ping/pong is transport-level liveness only. Send queues are bounded; slow clients are disconnected rather than silently dropping their data. The maximum label JSON size is 128 KiB to accommodate escaping of large raw barcodes; readings are never truncated. The client checks the JSON envelope and structured version-specific fields, but imposes no raw X content rules. Duplicate, extra or mistyped JSON properties and unknown versions are rejected. Update both `Scanner.Client.dll` and `Scanner.Contracts.dll` for C support; earlier DLLs reject unsupported versions. The test client automatically reconnects after connection loss while Connect is active.

The server emits multiple distinct barcode payloads independently, including mixed versions/symbologies in one frame. For camera readings of all current and future versions including X, identical decoded strings are suppressed for 500 ms from the previous broadcast to at least one connected client. Observations during the interval do not extend it. The key is the original decoded string, not extracted supplier fields, and whitespace is significant. A continuously visible code can be sent again once that interval expires. A client joining during a cooldown may wait until the next eligible observation. Reader readings, including identical consecutive values, are all sent without the 500 ms filter. There is no duplicate gate shared between ports. This is a stream of readings, not exactly-once inventory operations.

See the repository README for the exact payload grammar and CRC-32 printer test vectors. All older label/image/feedback protocols are retired.
