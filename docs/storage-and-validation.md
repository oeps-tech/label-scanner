# Validation and storage

No scan database, audit trail, label images, model packages or exports are created by the application. Server and client persist only their connection/camera preferences. Latest data, diagnostic results and counters are in memory. Existing legacy evidence files are not opened or deleted.

Routing order: validate OEPS versions 1/2/C, parse recognized supplier formats as version 3, otherwise use raw version X. Every decoded string produces a message classification; nothing is discarded because validation failed. Failed OEPS or supplier validation becomes X, not a validated version. The camera uses a 500 ms duplicate rule; barcode-reader readings have no suppression and go only to the separate reader port.

OEPS validation order remains: supported literal version (`1`, `2` or `C`), exact field count separated by a single `*`, version-specific field rules, eight-uppercase-hex checksum shape, CRC-32/IEEE equality. OEPS input is never trimmed or rewritten. CRC is checked on exact ASCII input before the final `*` and checksum. Double-asterisk separators fail structured validation.

Version 1 has five encoded fields: version, PN, lot, quantity and checksum. PN grammar, lot grammar/MMYY ranges and quantity grammar are unchanged. Quantity is preserved as a string; zero is valid.

Version 2 has six encoded fields: version, `sales_order_id`, `document_name`, `out_id`, `out_number`, checksum. Both record IDs must contain digits only and have values from 1 to 2147483647; they become JSON integers. Both printed numbers must be nonblank printable ASCII without `*` or control characters. Spaces, slashes and letter case are preserved; no fixed prefix is assumed. `document_name` is supplied by the printer, not replaced with Odoo's `name`. The scanner performs no Odoo lookup, relationship check or authorization check. Opening the records is the consuming application's responsibility.

The Lot begins with four digits `MMYY`: month `MM` must be `00`–`12`, and year `YY` must be `00` or `21`–`99`. Month zero and year zero are independently allowed. Years `01`–`20` are rejected; there is no additional check against the current date. The same constraints apply when the client DLL validates received JSON.

Version 3 extracts Worldway `mc`/`pm`/`qty` or ISO 15434 format 06 `P`/`1P`/`Q`. OEPS PN is found as a complete whitespace-delimited token using the existing version 1 grammar; zero or multiple distinct valid matches yield null. Missing/blank MPN yields null. Extracted field boundaries are trimmed. Acceptance requires **valid quantity AND (valid OEPS PN OR nonempty MPN)**. Quantity must be digits with an optional decimal dot and stays a string; zero is valid. Missing either identifier is allowed, but missing both, invalid quantity, duplicate relevant fields or malformed records causes raw X fallback. Actual RS/GS/EOT and their literal angle-bracket notation are parsed on a copy; no replacement is applied to fallback X text. Supplier parsers are separate functions in `SupplierLabelParser` so new formats can be added with their own fixtures.

Version C has three encoded fields: uppercase `C`, `command`, checksum. Commands must be nonblank printable ASCII without `*` or control characters. The complete payload is at most 4,096 characters; the command is at most 4,085. CRC-32/IEEE covers the exact `C*<command>` text. Whitespace and case are not changed. There is no fixed list of names: new or retired commands are managed by the consuming application. A valid command produces exactly `label_version` (string `"C"`) and `command` (string). The client DLL checks the same text rules. The scanner does not execute commands. Invalid command labels become X, preserving the original text.

Version X preserves the decoded text, without content rules, normalization, an X prefix or checksum. The decoder uses ZXing Plain text mode, retaining control characters and using ECI/charset information for Unicode, rather than ASCII replacement or human-readable separator substitution. Arbitrary binary payloads do not define a text encoding; X is decoded text, not a binary export. Network frames retain a 128 KiB limit and are never truncated.

Camera duplicate suppression uses monotonic time and is independent for each exact decoded string, across every current and future label version including X. Only a broadcast queued to at least one client starts its 500 ms interval. Observations inside the interval do not extend it. Supplier parsing does not change the duplicate key. Reader readings never enter this duplicate gate. Each source has its own monotonic idle timer, reset only by its own clients or debug override. Reader-only client demand does not open the camera.
